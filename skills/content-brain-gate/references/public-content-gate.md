# 公开内容生产大脑硬门禁

> 版本：2026-07-23
> 适用范围：口播、抖音短视频、公众号文章、图文、直播提纲、商业内容及其他准备公开发布的内容。
> 事故依据：[[07_知识库治理/2026-07-18_口播内容大脑事故根因与修复验收]]
> 便携说明：这是项目随仓库分发的规则快照；检测到个人知识库现行版时，以个人知识库现行版为准，本文件不反向覆盖个人知识库。

## 导航

1. 最高目标与不可跳过的输入
2. 状态机与来源完整度门
3. 最近六条查重、选题增量与观众距离
4. 机制解释、本人声音与 Skill 调用合同
5. 抖音精选质量目标、内容先于包装、最终交付和回归测试

## 一、最高目标

内容生产不是把资料改写成一篇流畅文稿，而是让一个明确的人看完后发生一种可观察变化：理解一个以前不懂的机制、修正一个判断、拿走一个工具、完成一个动作，或看见一个有边界的真实结果。

以下内容不得进入成稿：

- 只有热点复述，没有观众利益；
- 只有概念分类，没有机制解释；
- 只有“AI 很重要、要落地、从小事开始”等旧结论，没有新增证据；
- 只有作者身份和态度，没有陌生观众也愿意拿走的东西；
- 素材只有标题或元数据，却被写成原作者完整观点；
- 文案未通过，已经开始做封面、动效、音效或成片。

## 二、不可跳过的输入

任何公开内容任务开始时，必须先取得并记录以下输入：

1. 项目 `AGENTS.md` 和项目内容规范；
2. 项目启动脚本输出的本轮必读清单；
3. 最近六条已发布、已拍摄或已确认内容的标题、核心主张、证据、交付物和行动引导；
4. 当前账号声音档案；没有声音档案时，先从 5—20 条真实口播转写或用户确认稿建立；
5. 本轮全部来源的完整度、证据等级和允许用途；
6. 当前账号阶段及一句“现有证据只证明什么”。
7. 使用参考内容的叙事或 Talking 结构时，必须锁定用户原始目标、参考内容负责与不负责的作用、必需故事线和禁止改写主题。

无法取得某项输入时，必须明确写为缺失项并降级或停止，禁止默认为“已读取”。

其中第 7 项必须写入 `brief_contract`。事实纠偏、项目边界和抖音精选质量只能守住或验收原主题，除非用户明确要求，不得替换原主题。缺少意图锁时，即使来源、事实和表达质量全部通过，也必须保持 `blocked`。

## 三、状态机

每个内容任务只能处于以下一种状态：

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `blocked` | 输入、来源、证据、差异或机制不足 | 补调查、补原文、删选题、改范围 |
| `ready-for-outline` | 来源和新主张成立，但尚未形成完整结构 | 写选题卡和提纲 |
| `ready-for-draft` | 提纲、机制卡、证据边界和声音输入齐全 | 写第一版文稿 |
| `ready-for-production` | 文稿通过事实、重复、声音、朗读和合规复核 | 设计分镜、V6、动效、音效、封面和成片 |

状态不得由模型口头自报，必须由内容门禁卡和校验结果支撑。`ready-for-draft` 不等于可以拍摄；`ready-for-production` 仍需用户最终确认。

## 四、来源完整度门

### 1. 来源等级与允许用途

| 来源状态 | 可以做什么 | 禁止做什么 |
|---|---|---|
| `metadata-only` | 记录作者、标题、链接、发布时间线索；生成待调查列表 | 提炼主要观点、复述原意、分析 Talking 链路、判断爆款机制、模仿口吻 |
| `partial` | 只分析已经取得的片段，并标明缺口 | 把片段冒充完整内容、推断未取得的上下文 |
| `complete-user-pasted` | 在用户确认完整的范围内做结构和观点分析 | 冒充平台原始字幕或官方逐字稿 |
| `complete-transcript` | 做观点、结构、机制和表达拆解；精确引语仍需回听 | 把机器转写直接冒充精确逐字引语 |
| `primary-source` | 支撑与原页直接一致的事实和口径 | 超出原页范围做因果、效果或普遍性结论 |

### 2. 成功语义必须拆开

系统必须分别报告：

- `record_created`：来源卡是否创建；
- `content_acquired`：正文、字幕或音视频是否取得；
- `metrics_acquired`：播放、点赞、收藏等指标是否取得；
- `analysis_eligible`：是否有资格做观点和结构分析；
- `draft_evidence_eligible`：是否有资格进入公开文稿的证据链。

禁止只用“成功多少条”概括以上不同状态。

### 3. 素材不足时的固定动作

依次选择：

1. 从用户已授权的本地视频或音频转写；
2. 请用户提供完整字幕或原文；
3. 查找同一作者或机构的一手公开版本；
4. 将用途降级为标题线索；
5. 删除该素材，不为了凑数量推断内容。

## 五、最近六条查重门

写选题前必须建立最近六条台账，每条至少记录：

- 标题和日期；
- 服务对象与具体问题；
- 唯一主张；
- 核心证据；
- 观众可带走的东西；
- 结论和行动引导；
- 已经用过的关键比喻、结构和身份句。

新选题必须逐条回答：

1. 新问题是什么；
2. 新信息是什么；
3. 新证据是什么；
4. 新交付物是什么；
5. 如果删掉热点名和产品名，它是否仍然与最近六条不同。

只更换标题、展会、行业、产品、案例名、比喻或开头，不算新内容。

项目内已经冻结的母题只能作为一句背景，不得再次成为主结论。命中冻结母题而没有新证据、反例或结论变化时，状态必须是 `blocked`。

### 候选题生成不等于选题验证

允许使用 25 格、曼陀罗、关键词组合、人群 × 场景 × 问题等方法扩大候选池，但这些方法只解决“想不到题”，不证明“这个题值得拍”。

使用组合式选题工具时必须保留以下记录：

```text
使用的候选生成方法：
本次选中的候选题：
组合依据：行业内容 / 目标人群 / 具体场景
明确确认：候选生成不等于验证
观众问题是否成立：
与最近六条是否有新增量：
是否有本人事实或可靠证据：
是否符合账号当前阶段：
观众能否带走明确判断或动作：
被删除或暂缓的候选题：
```

固定纪律：

- 25 格和三点连线只能进入候选生成层，不得单独让内容门禁通过；
- 单条参考视频的高点赞、高收藏或高分享，只证明该作品在观察时点获得互动，不能证明同类选题可以稳定复制；
- 同行拍过、多个关键词能组合、AI 能生成完整文稿，都不能替代观众问题、内容增量、证据、账号阶段和交付物检查；
- 五项验证未全部通过的组合，只保留在线索池，不进入提纲或写稿；
- 发布后的真实反馈用于校正选题判断，但不得用一次爆或一次不爆总结普遍规律。

## 六、选题增量门

每条内容在写提纲前必须完成一张第一性原理选题卡：

```text
服务谁：
他此刻的具体问题：
看完要改变的状态：
唯一新主张：
与最近六条相比新在哪里：
现有证据只证明：
证据不能证明：
观众可带走什么：
不适用边界：
可以删除的材料：
```

判断顺序固定为：

```text
先确定观众问题
→ 再找能解释问题的机制
→ 再选择必要案例和产品
→ 删除不服务主张的素材
→ 最后才组织表达
```

禁止先按“算力、模型、应用”或“第一个、第二个、第三个产品”凑齐分类，再反向寻找与普通人的关系。

## 七、观众距离与账号阶段门

事实正确、信息新、机制讲清，仍不等于适合当前账号公开讲。写提纲前必须确认内容与目标观众、讲述者真实身份和账号当前阶段匹配。

每条内容必须回答：

```text
账号当前处于调查、试验、结果、方法还是复制阶段：
讲述者在本题中的真实位置：
前20秒观众在哪个具体工作或生活场景认出自己：
高层技术、专家观点或大公司产品在本稿中是主角、证据还是背景：
至少两个普通人可以直接感知的场景：
观众最终得到的认同、判断或行动：
哪些内容需要专家身份或真实结果，本账号当前不能替代：
```

固定纪律：

- 当前账号以本地 AI 实践者和复杂信息翻译者身份表达，不冒充科学家、芯片架构师、医疗专家或已经取得规模化结果的方法导师；
- 高层技术、院士观点、政策和大公司产品，除非账号有相称的一手经历和证据，只能承担必要证据或背景，不能长期占据主叙事；
- 前20秒必须让目标观众看见一个与自己工作、行业或生活直接相关的具体场景，不能先花一分钟解释专业前提；
- 高层话题至少落到两个普通人可以看见、听见或经历的场景，并说明他们在其中的真实角色；
- 删除大会名、院士名和产品名后，观众仍应能说清这条与自己有什么关系；
- 内容的专业高度可以高于观众，但理解入口必须与观众同高。不能把“我能讲”误当成“我现在适合以这个身份讲”。

以下任一情况出现，状态必须退回 `blocked` 或 `ready-for-outline`：

- 技术产品和专家观点仍是主角，普通人只在结尾被硬接一次；
- 观众要先理解大量架构、参数和术语，才能知道与自己有什么关系；
- 讲述者需要依赖并不存在的专家身份、项目结果或行业权威才能成立；
- 举例只有宏大产业和未来趋势，没有普通人可感知的现场；
- 内容很正确，但目标观众不会自然产生“这说的是我”的认同。

## 八、机制解释门

每一个承担核心论证的产品、案例、政策或技术，必须填写机制卡：

```text
对象名称：
它解决的真实问题：
原来的瓶颈：
它用什么关键方法工作：
能观察到的变化：
本轮一手或高质量证据：
证据准确证明什么：
证据不能证明什么：
与目标观众的直接关系：
最容易讲错或误用的边界：
```

以下表达不算讲清机制：

- 只报参数、价格、发布日期或展品数量；
- 只说“更快、更强、更便宜、更智能”；
- 只说“让很多卡像一台机器协同”，却不解释原有等待发生在哪里；
- 只说“接进真实业务”，却不说明输入、处理、输出、复核和失败条件；
- 用一个生动比喻替代真实原理。

复杂技术可以用大白话，但大白话必须与真实机制逐项对应。

## 九、本人声音门

声音档案只能来自用户真实口播转写、用户亲自改定的文稿和明确表达偏好，不能从通用爆款模板或 AI 生成稿反推。

声音档案至少包括：

- 身份与观众关系；
- 常用开场方式；
- 解释复杂概念的方法；
- 句长、节奏、反问和停顿特点；
- 如何表达判断、不确定性和边界；
- 可以稳定保留的表达；
- 已经用滥或用户明确反感的表达；
- 事实和经历禁区。

“像本人”不等于重复本人说过的同一结论。已冻结母题、身份句和行动模板不能因为出现在真实转写里就继续复用。

成稿必须通过：

1. 事实锁；
2. 去 AI 味检查；
3. 大声朗读检查；
4. 与声音档案的差异检查；
5. 与最近六条的主张级查重。

## 十、Skill 调用合同

不要求为了形式调用所有 Skill，但以下能力缺一不可：

| 阶段 | 必需能力 | 失败动作 |
|---|---|---|
| 抖音素材进入知识库 | `ingest-douyin-knowledge` | 保留真实完整度，不得把建卡写成深度拆解成功 |
| 事实、数据、产品机制 | 深度研究或一手来源检索 | 无来源则降级为观点或删除 |
| 声音档案缺失或失真 | `brand-voice` | 先建立或更新档案，不直接套通用模板 |
| 选题与写稿前 | 全局内容大脑门禁 Skill | 未通过只能补资料或改选题 |
| 成稿定稿前 | `humanize-koubo-script` 与中文模式检查 | 事实保真不足则撤回改写 |
| 进入制作后 | 口播导演、Remotion、动效与音效能力 | 内容未到 `ready-for-production` 时禁止调用 |

调用过某个 Skill 不能自动证明结果合格。验收看输入、输出和门禁证据，不看工具名称数量。

## 十一、抖音精选内容质量目标层

事实硬门禁回答“这条内容能不能写、能不能拍”；精选质量目标回答“观众为什么愿意看完、记住和带走”。二者不得混为一谈。

抖音官方公开指南和用户提供的页面截图将优质内容特征概括为：

- 获得感：有知识、经验或见解，深入浅出，让观众得到启发和收获；
- 惊喜感：选题、立意或表达有真实创新，让观众眼前一亮；
- 表达力：把想法、感受和信息说得清楚、准确、生动；
- 感染力：从真实体验和感受出发，真诚表达并触发共鸣。

项目内固定规则：

1. 新门禁卡使用 `schema_version: 3`，填写 `douyin_quality`，并在实际文稿形成后补齐绑定稿件与两项文案 Skill 哈希的 `copy_review` 报告。
2. 本账号把获得感和表达力设为每条内容的主目标。
3. 惊喜感必须来自新问题、新证据、新机制或新表达，不能来自夸张和隐去边界。
4. 感染力必须来自真实经历和真实感受；没有材料时允许不强求，禁止虚构。
5. 每一项必须写正文证据和观众验收方式，不能只填主观分数。
6. `production` 阶段必须由用户人工复核，机器不能宣布作品“已经有感染力”。
7. 必须明确 `selection_not_guaranteed: true`。平台是否标记精选、是否给流量，只能由真实平台结果证明。

详细口径见 `<project-root>/knowledge/15-抖音精选内容质量验收.md`。

质量层不能反向放行来源、事实、查重、机制、观众距离、合规和用户确认。内容对象错误时，表达再精彩也必须退回。

## 十二、内容先于包装门

只有 `ready-for-production` 才允许开始：

- 分镜和拍摄素材计划；
- GPT 生图或生视频提示词；
- V4/V5/V6 卡片和信息动效；
- 音效点位和音效生成；
- 封面提示词；
- 正式剪辑和成片渲染。

如果内容门被打回，所有包装工作暂停。不得用更强钩子、更炫画面或更多音效掩盖信息增量不足。

## 十三、最终交付前检查

每条内容必须附带简版验收记录：

```text
内容状态：
来源完整度检查：通过/失败
最近六条查重：通过/失败
唯一新主张：
机制卡：通过/失败
声音档案：已读/缺失
事实锁：通过/失败
去 AI 味与朗读：通过/失败
抖音精选质量目标：获得感/惊喜感/表达力/感染力的正文证据与人工复核状态
合规与公开边界：通过/失败
用户最终确认：待确认/已确认
```

任何一项失败，状态不得写为 `ready-for-production`。

## 十四、回归测试纪律

每次发生“重复、扭曲原意、机制讲不清、规则未读取、素材状态误判”等事故，必须：

1. 保留失败样本；
2. 把用户反馈翻译成机器可检查条件；
3. 新增一个失败测试；
4. 修复规则或校验器；
5. 确认旧失败样本稳定失败；
6. 确认合格样本稳定通过；
7. 再生成新内容；
8. 由真实用户和发布结果继续验证。

禁止只重写当前稿件而不修复产生它的流程。
