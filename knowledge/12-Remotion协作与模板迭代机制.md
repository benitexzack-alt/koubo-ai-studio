# Remotion 协作与模板迭代机制

> 日期：2026-07-05
> 状态：已确认执行。后续每条口播视频都按本机制复盘和迭代。

## 一、分工原则

用户负责真实表达和一线素材：

- 选题判断。
- 口播录制。
- 剪映粗剪。
- 真实截图、门店素材、客户案例素材。
- GPT / ImageTo 封面生成。

Codex + Remotion 负责结构化包装：

- 转写、字幕校正和语义拆段。
- 生成 `visual-plan.json`。
- 制作提示卡、流程图、对比卡、清单卡、指标卡等动效片段。
- 渲染预览、抽帧检查、技术验证。
- 复盘每条视频的动效经验，并逐步沉淀成项目 Skill。

## 二、已确认加入的三项机制

### 0. 当前最高生产基线

Remotion 模板不是一次性效果，而是持续升级的生产基线。

硬规则：

- 每条正式成片默认使用当前最高生产基线。
- 新片只能在当前基线上升级，不能退回简版、旧版或临时拼接版。
- 当前基线升级后，旧基线自动成为历史版本，不再作为正式成片默认方案。
- 如果临时使用 `ffmpeg` 静态卡片、无动效字幕或无 HUD 包装，只能叫“快速样片”或“简版预览”，不能叫正式成片。

当前基线核心模块：

- 数字运镜层：底层视频轻推拉、轻横移、金句 punch-in，字幕/HUD/信息卡保持稳定。
- 顶部栏目条。
- 右上主题条。
- 底部进度条。
- 语义动效卡片：观点卡、对比卡、清单卡、流程卡、指标卡至少按内容选择使用。
- 中文语义字幕动效。
- 如需双语，英文只做辅助字幕，不能抢中文主字幕。

当前基线验收方式：

- 渲染 20-30 秒预览。
- 预览需覆盖钩子、复杂叠层、每类全屏素材和结尾行动引导。
- 视觉方案必须通过图层标题归属校验，抽帧确认核心模块存在。
- 必须用最终成片音轨重新转写并复算双语同步。
- 用户确认后再渲染全片。
- 正式片必须通过发布记录校验，用户完整观看后才可标记为验证通过。

当前机器可读基线文件：`workflow/production-baseline.v1.json`。

### 0.1 数字运镜默认工作流

从 2026-07-08 起，所有正式口播默认启用数字运镜层。

目标：

- 避免固定机位长期不动造成呆板感。
- 在金句、结论、反常识判断处给观众一个轻微视觉落点。
- 在长时间普通讲述中保持细微呼吸感，不抢字幕和信息卡。

技术规则：

- 数字运镜只作用于底层视频画面，字幕、顶部 HUD、进度条、信息卡和关键词卡不跟随移动。
- 普通句：持续轻微呼吸式移动，缩放控制在约 `103%-104%`。
- 长句或普通讲述：慢速推近或轻横移，不制造晃动感。
- 金句、关键词、结尾判断：配合 `keyword-pop` 或重点 beat 做一次短促 punch-in，峰值不超过约 `106%`。
- 段落切换：允许轻微重置构图，但不能造成跳帧、闪动或观众察觉的硬切。

硬边界：

- 禁止为了“有动感”频繁推拉、抖动、旋转或模拟手持晃动。
- 禁止数字运镜把脸、手势、字幕、信息卡推到安全区之外。
- 如果原片已经是近脸构图，数字运镜必须降强度；宁可少动，也不能压迫。
- 预览质检必须抽查至少一个普通长句和一个金句 punch-in 点。

当前已落地能力：

- `remotion/src/components/DigitalCameraVideo.tsx`。
- `AIBizTalk16x9` 默认使用数字运镜层承载底层视频。

### 1. 每条视频先做 `visual-plan.json`

任何视频进入 Remotion 前，先生成视觉方案，不直接写动效代码。

`visual-plan.json` 必须回答：

- 哪句话触发动效？
- 动效从几秒到几秒？
- 是观点卡、对比卡、清单卡、流程卡、指标卡、截图卡还是 OCR 标注卡？
- 对应数字运镜是什么：普通慢推、轻横移、金句 punch-in、段落构图重置，还是保持静止？
- 文案是什么？
- 放左侧还是右侧？
- 会不会挡脸、挡手、挡字幕？
- 素材来源是真实截图、AI 背景、图表库、地图插件，还是纯 Remotion 组件？
- 哪些参数需要暴露给后续调整？

从 2026-07-11 起，视觉方案还必须声明：

- `titleOwner`：本层是否承担当前画面的主标题。
- `overlapGroup`：哪些层会在同一画面组重叠。
- `zone`：占用左侧、右侧、中心、底部字幕安全区还是全屏。
- `reviewAt`：需要抽帧复查的风险时间点。

校验命令：`node tools/validate-visual-plan.mjs <visual-plan.json>`。同一 `overlapGroup` 同时出现两个标题拥有者时，必须在渲染前停止并修正。

### 2. Remotion 只做小动效片段，不替代整片剪辑

当前主路线：

```text
用户粗剪主视频
-> Codex 拆语义节点
-> Remotion 做局部动效/字幕强化/透明贴片
-> 技术验证
-> 用户人工观看确认
```

Remotion 的定位是“精确包装工具”，不是剪映或达芬奇的替代品。

适合 Remotion 的内容：

- 标题条、栏目条、进度条。
- 观点卡、对比卡、清单卡、流程卡、指标卡。
- 工具界面截图包装。
- 数据图表、路径图、局部高亮。
- 可复用的透明动效片段。

暂不让 Remotion 承担：

- 大规模粗剪。
- 情绪化实拍调色。
- 复杂实拍转场。
- 封面终稿生成。

### 3. 复杂参数配置化

所有高频调整项优先进入配置，不在组件里硬编码。

优先配置化的参数：

- 卡片类型：`statement`、`compare`、`checklist`、`flow`、`metric`、`screenshot`、`ocr-callout`。
- 卡片位置：`left`、`right`、`top-left`、`top-right`。
- 颜色：主色、强调色、风险色、成功色。
- 入场时间、停留时间、退出时间。
- 字号、最大宽度、行数限制。
- 需要避开的区域：脸、手、字幕、安全区。
- 是否导出透明动效。

原则：第一次可以手调，第二次复用就要进入配置，第三次必须模板化。

## 二点五、字幕与剪辑时间轴规则

剪辑后的字幕必须以输出时间轴为准。

正确公式：

```text
输出字幕时间 = 原词级时间 - 当前保留片段起点 + 前面所有保留片段累计时长
```

禁止行为：

- 禁止按原稿手工估字幕时间后直接用于正式成片。
- 禁止只检查字幕是否挡脸，不检查字幕是否跟嘴。
- 禁止把“内容主线一致”当成“字幕时间对齐”。

允许行为：

- 可以手工校正错字、术语和标点。
- 可以为英文辅助字幕做语义概括，但英文字幕仍必须落在对应输出片段时间范围内。

## 二点六、中英双语字幕规则

中英双语正式口播必须使用同一输出时间轴。

默认方案：

- 中文按句群或语义短句分页。
- 英文是该中文句群的对应译文或语义压缩译文。
- 中文和英文共用同一个 `startMs/endMs`。
- 中文为主字幕，英文为辅助字幕，英文不得抢占中文可读性。

禁止行为：

- 禁止中文字幕和英文字幕使用两套互不约束的时间轴直接叠加。
- 禁止英文辅助字幕跨过中文大段、信息卡或关键词卡长期悬挂。
- 禁止只看英文大意正确，不检查它是否和当前中文同段。

中文标点渲染规则：

- 逗号、句号、问号、感叹号、顿号、冒号、分号必须绑定前一个字，不得独立换行。
- 中文标点应比正文略小，并向右下方偏移，避免出现在字的正中间。
- 抽帧质检必须包含至少一个长句和一个结尾句，专门检查标点是否掉行。

长句可读性规则：

- 中文有效字数或英文长度超过安全阈值时，字幕框必须自动扩展安全宽度、降低中英字号并微调底部边距。
- 禁止用固定字号硬塞长句，导致英文过密、中文压脸或底部信息拥挤。

当前已落地能力：

- 双语句群字幕组件：`remotion/src/components/BilingualCaptionOverlay.tsx`。
- 第三条测试口播双语句群数据：`remotion/public/data/IMG_20260707_small_business_ai.bilingual.v3.json`。

## 二点七、关键词短动效规则

关键词动效用于补足大卡片之间的表达重点，不替代主字幕和主卡片。

适用场景：

- 一句话里出现需要观众记住的核心判断。
- 需要把“问题根因 / 行动标准 / 安全边界 / 结尾金句”短促打亮。
- 大卡片已经退场，但口播仍有一个可被提炼的关键短句。

硬规则：

- 默认放在左侧安全区，避开脸、手和底部字幕。
- 出现时间应短，不长期压住画面。
- 文字必须来自当前口播语义，不为了好看新造概念。
- 每条视频新增关键词动效后，必须抽查其出现帧。
- 可以使用左侧色条、短横线、轻脉冲或标题自适应字号增强视觉落点，但不得抢走口播主体。

当前已落地能力：

- `Beat.variant` 支持 `keyword-pop`。
- `BeatCards` 已支持 `KeywordPopOverlay`。

## 三点五、升级不回退机制

- 当前标准、升级待办、风格参考和发布记录分别存放于 `workflow/production-baseline.v1.json`、`workflow/upgrade-backlog.json`、`workflow/style-library/`、`workflow/releases/`。
- 用户给出的参考图先变成风格卡和验收标准，再决定是否进入单条实验；不能因一句“昨天更好”而回滚到旧模板。
- 事实型问题（错位、叠层、遮挡、漏字幕）按修复处理，校验通过后进入当前基线。
- 风格型升级（封面、动效、色彩、构图）一次只验证一个主实验；连续三条稳定并得到用户确认或数据支持后再提升基线版本。
- 发布 24 小时后必须回填封面、标题、留存、完播、互动和有效咨询，作为是否推广模板的真实依据。

## 四、OCR 指哪打哪机制

“OCR 指哪打哪”的意思是：先识别截图或视频帧里的文字和坐标，再让 Remotion 根据坐标画高亮、箭头、框选或马克笔。

适用场景：

- 讲工具界面时，精准圈出某个按钮、菜单、设置项。
- 讲报告或网页时，精准标注某一句话。
- 讲聊天记录时，突出某条客户反馈。
- 讲数据后台时，高亮某个指标、图表或异常值。

基础流程：

```text
截图/视频帧
-> OCR 识别文字和位置
-> 人工或 AI 选择要强调的词
-> 生成 ocr-callout 节点
-> Remotion 画框、箭头、马克笔或放大镜
```

当前已落地的基础能力：

- OCR 识别脚本：`tools/ocr-image.mjs`。
- Remotion 动效类型：`ocr-callout`。
- 开发验收 composition：`AIBizTalk16x9-OCRDemo`。
- 单帧验收命令：`cd remotion && npm run still:ocr-demo`。

边界：

- OCR 是辅助定位，不是证据本身。
- 客户、合同、聊天记录、后台数据必须先脱敏。
- OCR 坐标需要抽帧复查，不能直接相信。

## 五、后续 Skill 化方向

连续完成 3-5 条视频后，把稳定机制抽成项目 Skill：

```text
koubo-remotion-director
```

候选能力：

- 读取口播粗剪和转写。
- 自动生成 `visual-plan.json`。
- 按主题选择动效组件。
- 自动避开脸、字幕和安全区。
- 生成 Remotion 样片。
- 输出复盘和下一条升级建议。
